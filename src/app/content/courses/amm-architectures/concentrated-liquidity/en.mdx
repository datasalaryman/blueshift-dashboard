# Concentrated Liquidity

In May 2021, Uniswap V3 launched with a radical redesign. Instead of spreading liquidity across all prices from zero to infinity, LPs could concentrate their capital in specific price ranges.

The result: up to 4000x capital efficiency for tight ranges. The catch: dramatically more complexity for LPs, new MEV vectors, and math that makes StableSwap look simple.

Concentrated liquidity is now the dominant AMM design for major pairs. Understanding it is essential.

<ArticleSection name="The Capital Efficiency Problem" id="efficiency-problem" level="h2" />

### Where Does Liquidity Sit?

In constant product AMMs, liquidity is distributed across all possible prices:

```
ETH/USDC pool: $10M liquidity
Current price: $2,000/ETH

Liquidity available at:
- $1 - $100: ~$50K
- $100 - $500: ~$150K  
- $500 - $1,000: ~$300K
- $1,000 - $2,000: ~$1.5M ← Current range
- $2,000 - $3,000: ~$1.5M ← Current range
- $3,000 - $5,000: ~$600K
- $5,000 - $10,000: ~$400K
- $10,000+: ~$300K
```

Most of that liquidity will never be used. ETH probably won't trade at $50 or $50,000 anytime soon. But the math allocates capital there anyway.

### The Utilization Problem

```
$10M total liquidity
±2% price range: ~$100K active liquidity
Utilization: 1%
```

99% of LP capital is sitting idle, earning no fees. LPs are providing liquidity for price ranges that don't exist in reality.

### What If LPs Could Choose?

Concentrated liquidity lets LPs say: "I want to provide liquidity between $1,800 and $2,200."

All their capital works within that range. If price stays there, they earn fees on 100% of their deposit, not 1%.

<ArticleSection name="The V3 Model" id="v3-model" level="h2" />

### Positions Instead of Pool Shares

In V2, all LPs share one pool. In V3, each LP has a distinct position:

```
Position 1: $50K liquidity from $1,800 - $2,200
Position 2: $20K liquidity from $1,500 - $2,500
Position 3: $100K liquidity from $1,900 - $2,100
```

Each position is represented as an NFT (not a fungible LP token). Positions can overlap, creating deeper liquidity at popular price points.

### Active vs Inactive Liquidity

A position only earns fees when price is within its range:

```
Current price: $2,000

Position A ($1,800 - $2,200): ACTIVE - earning fees
Position B ($2,300 - $2,800): INACTIVE - earning nothing
Position C ($1,500 - $1,700): INACTIVE - earning nothing
```

If price moves to $2,500, Position A becomes inactive and Position B becomes active.

### The Composition Shift

When price moves within a range, the position's composition changes:

```
Position: $1,800 - $2,200, $10K initial value

At $1,800 (lower bound): 100% ETH, 0% USDC
At $2,000 (middle): ~50% ETH, ~50% USDC  
At $2,200 (upper bound): 0% ETH, 100% USDC
```

If price drops below $1,800, you hold only ETH. If it rises above $2,200, you hold only USDC. This is impermanent loss amplified.

<ArticleSection name="Ticks and Tick Spacing" id="ticks" level="h2" />

### Price Space is Discretized

V3 doesn't allow arbitrary price ranges. Prices are divided into discrete "ticks":

```
Each tick represents a 0.01% (1 basis point) price change.

Tick 0 = price 1.0000
Tick 1 = price 1.0001
Tick 100 = price 1.0100
Tick -100 = price 0.9901
```

The formula:

```
price(tick) = 1.0001^tick
tick(price) = log(price) / log(1.0001)
```

### Why Ticks?

**Gas efficiency**: Storing exact liquidity at every possible price is impossible. Ticks create a finite set of price points.

**Aggregation**: Multiple positions ending at the same tick can be aggregated.

**Precision**: 1 basis point spacing is fine enough for most use cases.

### Tick Spacing

Not every tick is usable. "Tick spacing" determines which ticks are valid:

| Fee Tier | Tick Spacing | Price Increment |
|----------|--------------|-----------------|
| 0.01% (stables) | 1 | 0.01% |
| 0.05% | 10 | 0.10% |
| 0.30% | 60 | 0.60% |
| 1.00% | 200 | 2.00% |

Higher fee tiers have wider tick spacing, reducing gas costs for volatile pairs where precision matters less.

### The Tick Bitmap

V3 uses a bitmap to track which ticks have liquidity:

```rust
// Bitmap: each bit represents whether a tick is initialized
// Position in bitmap = tick_index / 256
// Bit position = tick_index % 256

fn is_tick_initialized(tick_bitmap: &[u256], tick: i32) -> bool {
    let word_pos = tick >> 8; // tick / 256
    let bit_pos = tick % 256;
    let word = tick_bitmap[word_pos as usize];
    (word >> bit_pos) & 1 == 1
}
```

When swapping, the contract only needs to check initialized ticks, not every possible price.

<ArticleSection name="The Math" id="math" level="h2" />

### Virtual Reserves

Within a tick range, V3 still uses x*y=k, but with "virtual" reserves:

```
Real reserves: what the position actually holds
Virtual reserves: what reserves would be if liquidity extended to 0 and ∞
```

The key insight: concentrated liquidity behaves like a larger x*y=k pool within its range.

### Liquidity (L)

In V3, liquidity is defined as:

```
L = sqrt(x * y)

Where:
- L = liquidity
- x = virtual reserve of token X
- y = virtual reserve of token Y
```

L remains constant as swaps occur (within a tick range). Only the ratio of x to y changes.

### Price as Square Root

V3 uses sqrt(price) internally:

```
√P = sqrt(price of token1 in terms of token0)

Price = (√P)²
```

Why? It simplifies the math for liquidity calculations:

```
x = L / √P  (amount of token0)
y = L * √P  (amount of token1)
```

### The Core Swap Formula

For a swap within a single tick range:

```
Δ√P = Δy / L    (when swapping token0 for token1)
Δ√P = Δx * L    (when swapping token1 for token0)

Where:
- Δ√P = change in sqrt price
- Δy = amount of token1 added
- Δx = amount of token0 added
- L = liquidity
```

### Position Bounds

A position between price_lower and price_upper contributes:

```
token0_amount = L * (1/√P_current - 1/√P_upper)
token1_amount = L * (√P_current - √P_lower)

Only when: P_lower ≤ P_current ≤ P_upper
```

<ArticleSection name="Crossing Ticks" id="crossing-ticks" level="h2" />

### What Happens at Tick Boundaries

When a swap pushes price past an initialized tick, liquidity changes:

```
Price moving from $2,000 to $2,100

At tick for $2,050:
- Position A ($1,900-$2,050) ends: remove its liquidity
- Position B ($2,050-$2,200) begins: add its liquidity

Total liquidity = Σ(all active positions)
```

### The Tick Crossing Algorithm

```rust
fn swap(amount_in: u128, zero_for_one: bool) -> u128 {
    let mut amount_remaining = amount_in;
    let mut amount_out = 0u128;
    let mut current_tick = self.current_tick;
    let mut current_sqrt_price = self.sqrt_price;
    let mut current_liquidity = self.liquidity;
    
    while amount_remaining > 0 {
        // Find next initialized tick
        let next_tick = self.next_initialized_tick(current_tick, zero_for_one);
        let next_sqrt_price = tick_to_sqrt_price(next_tick);
        
        // Compute swap within this tick range
        let (amount_in_step, amount_out_step, sqrt_price_next) = 
            compute_swap_step(
                current_sqrt_price,
                next_sqrt_price,
                current_liquidity,
                amount_remaining,
            );
        
        amount_remaining -= amount_in_step;
        amount_out += amount_out_step;
        current_sqrt_price = sqrt_price_next;
        
        // If we reached the next tick, cross it
        if sqrt_price_next == next_sqrt_price {
            current_liquidity = self.cross_tick(next_tick);
            current_tick = if zero_for_one { next_tick - 1 } else { next_tick };
        }
    }
    
    // Update state
    self.sqrt_price = current_sqrt_price;
    self.current_tick = current_tick;
    self.liquidity = current_liquidity;
    
    amount_out
}
```

### Gas Implications

Each tick crossing costs gas. A swap through many tick ranges is expensive:

```
Small swap (within one tick range): ~100K gas
Large swap (crossing 10 ticks): ~300K gas
Very large swap (crossing 50 ticks): ~800K gas
```

This is why tick spacing exists. Wider spacing = fewer crossings = cheaper swaps.

<ArticleSection name="Impermanent Loss Amplified" id="impermanent-loss" level="h2" />

### Concentrated IL

Concentrated liquidity amplifies impermanent loss within the range:

```
Full range position (like V2):
- 2x price change → 5.7% IL

Position from P to 2P (concentrated):
- 2x price change → position entirely in one token
- If price returns: no loss
- If price doesn't return: effectively sold at average of range
```

### The Math

For a position between prices P_a and P_b:

```
IL = 2 * sqrt(P_current/P_initial) / (1 + P_current/P_initial) - 1

Concentrated IL multiplier ≈ sqrt(P_b/P_a)
```

Tighter range = higher multiplier = more IL if price exits range.

### Out-of-Range Positions

When price exits your range:

```
Position: $1,800 - $2,200
Price drops to $1,500

Result:
- Position holds 100% ETH (bought all the way down)
- Earning zero fees (out of range)
- Waiting for price to return
```

You've effectively placed a limit order. Price returning means you profit. Price staying low means you're holding a depreciating asset.

<ArticleSection name="JIT Liquidity and MEV" id="jit-mev" level="h2" />

### Just-In-Time Liquidity

MEV searchers exploit concentrated liquidity with a new attack:

```
1. See large swap in mempool
2. Add concentrated liquidity right at current price
3. Let the swap execute (earn most of the fees)
4. Remove liquidity in same block
```

The JIT provider captures fees that would have gone to long-term LPs, with zero impermanent loss risk (they're in and out instantly).

### Why This Works

Concentrated liquidity at exactly the current price captures maximum fees:

```
Long-term LP: $100K liquidity from $1,800 - $2,200
JIT LP: $100K liquidity from $1,999 - $2,001

Swap at $2,000:
- JIT position is 100x more concentrated
- Captures ~99% of the fees
```

### Defenses

**Time-weighted positions**: Some protocols require liquidity to be in range for minimum time.

**Fee tiers**: Higher fee tiers make JIT less profitable (more capital needed for same fee capture).

**Private mempools**: Reduce visibility of pending swaps (but don't eliminate the problem).

<ArticleSection name="Implementations" id="implementations" level="h2" />

### Uniswap V3 (Ethereum)

The original. Launched May 2021. 
- Business source license (couldn't be forked for 2 years)
- License expired April 2023
- Still dominant on Ethereum mainnet

### Orca Whirlpools (Solana)

Solana's primary concentrated liquidity implementation:
- Adapted V3 math for Solana's account model
- Integrated with Jupiter aggregator
- Tick arrays stored in separate accounts (Solana-specific optimization)

### Raydium CLMM (Solana)

Raydium's concentrated liquidity pools:
- Similar to Whirlpools
- Integrated with Raydium's broader AMM ecosystem
- Both CLMM and constant product pools

### Implementation Considerations

**Tick arrays**: Solana can't store unlimited ticks in one account. Implementations use multiple accounts (tick arrays) covering price ranges.

```rust
// Solana: tick array covers a range of ticks
pub struct TickArray {
    pub start_tick_index: i32,
    pub ticks: [Tick; TICK_ARRAY_SIZE], // e.g., 88 ticks per array
}
```

**Position NFTs**: Each position needs unique state. On Solana, this is typically a PDA per position.

**Precision**: sqrt price calculations need high precision. Use u128 or fixed-point libraries.

<ArticleSection name="Active Liquidity Management" id="management" level="h2" />

### The LP's Dilemma

Concentrated liquidity requires active management:

```
Set and forget (wide range):
- Lower capital efficiency
- Lower fees per dollar
- Less IL risk
- Simpler

Active management (tight range):
- Higher capital efficiency
- Higher fees per dollar
- Higher IL risk if price moves
- Requires constant attention
```

### Rebalancing Strategies

**Range orders**: Set asymmetric ranges expecting directional moves.

**Mean reversion**: Keep range centered on TWAP, rebalance when price deviates.

**Volatility-based**: Widen ranges during high volatility, tighten during calm.

### Automated Vaults

Protocols like Kamino (Solana) automate concentrated liquidity management:
- Algorithms rebalance positions
- Single deposit, automatic range management
- Trade-off: vault fees + smart contract risk

<ArticleSection name="When to Use Concentrated Liquidity" id="when-to-use" level="h2" />

### Ideal Use Cases

**High volume pairs**: ETH/USDC, SOL/USDC where fee income compensates for complexity.

**Professional LPs**: Market makers with active management capabilities.

**Range-bound markets**: Assets trading in predictable ranges.

### When NOT to Use

**Low volume pairs**: Complexity not worth it for minimal fees.

**Passive LPs**: If you can't actively manage, use full-range or V2-style pools.

**Highly volatile assets**: Price frequently leaving ranges → frequent rebalancing → gas costs.

### The Rule of Thumb

> Use concentrated liquidity when you have the sophistication to manage it and the volume justifies the complexity.

For most retail LPs, automated vaults or wider ranges are more practical than trying to compete with professional market makers.

<ArticleSection name="Key Takeaways" id="takeaways" level="h2" />

1. **Concentrated liquidity** allows LPs to focus capital in specific price ranges
2. **Up to 4000x capital efficiency** for very tight ranges
3. **Ticks** discretize price space; **tick spacing** varies by fee tier
4. **Virtual reserves** make the math work within ranges
5. **IL is amplified** when price exits your range
6. **JIT liquidity** is a new MEV vector unique to concentrated liquidity
7. **Active management** is required to maximize returns

Concentrated liquidity revolutionized capital efficiency but shifted complexity to LPs. It's the dominant design for high-volume pairs, but not universally superior.
